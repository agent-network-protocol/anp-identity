ANP E1 identity runtime

让应用使用身份，
而不是搬运私钥。

ANP Identity 是面向 ANP E1 DID 的安全身份托管与生命周期运行时。它把密钥保管、 KID 权限、并发写入、故障恢复和 DID 更新协调收进同一个边界，向应用提供按 KID 调用的签名、验证、密钥协商与 HTTP 请求认证能力。

E1 only Rust + Node.js / TypeScript Non-exportable private keys Apache-2.0 v0.1.0 pre-release

一句话定位

它是“身份密钥与 DID 状态的本地控制面”，不是 DID 托管服务，也不是消息系统。

应用提交 KID 和操作意图；模块在内部完成授权检查和密码学操作，仅返回签名、 公钥、共享秘密或公开文档，不返回托管私钥。

Overview

项目概览

ANP Identity 将“生成一份 DID 文档”升级为“长期、安全、可恢复地运营一个或多个 DID”。

01

它管理什么

ANP E1 DID、托管密钥、外部公钥、服务条目、版本、待发布修订和密钥生命周期。

02

它输出什么

DID 文档、公开元数据、签名、验证结果、HTTP 签名头，以及调用方继续派生的 X25519 共享秘密。

03

它保护什么

托管私钥不会出现在公开 Rust API、Node 对象、DTO、声明文件、日志、调试输出或错误消息中。

04

谁适合使用

ANP Agent、CLI、桌面端、服务进程、消息核心，以及需要在本机长期运营 E1 DID 的 DSH 插件。

01 · Problem

它要解决的问题

DID SDK 通常可以生成密钥和文档，但生产环境真正困难的是：私钥之后放在哪里、谁能用、 多进程如何不互相覆盖，以及发布到一半失败时如何恢复。

私钥扩散

如果每个业务模块、FFI 适配器和脚本都接触私钥，任何序列化、日志或错误路径都可能成为泄漏点。

权限语义模糊

“有一把 Ed25519 私钥”不等于它能签任意内容。HTTP 认证、文档根证明和 E2EE 断言需要不同角色约束。

状态与发布不一致

本地生成了新密钥，并不代表远端 DID 文档已经发布。超时后贸然回滚，可能删除远端已引用的密钥。

跨进程竞争

CLI、守护进程或多个 Worker 同时写同一身份时，普通文件写入很容易造成丢更新和部分状态。

崩溃后的半成品

创建身份或轮换密钥包含多次持久化；在任一点崩溃，都需要在下次打开时收敛到可解释状态。

多身份串线

同一进程托管多个 DID 时，需要保证某个身份的 KID 不能被另一个身份借用或错误解析。

核心问题不是“怎么生成一把密钥”，而是“怎么把身份作为长期状态安全地运营”。 ANP Identity 将这些通用但高风险的逻辑集中实现，避免每个产品重复建设一套自制 keystore 和发布状态机。
02 · Solution

它怎么解决

以 DidStore 作为持久化与并发边界，以 DidIdentity 作为单个 DID 的能力句柄， 底层复用 anp 的无状态协议原语，上层把网络发布与业务流程留给宿主。

宿主应用 CLI · Agent · DSH 插件 · 消息核心 表达操作意图，不读取私钥
→
ANP Identity DidStore → 多个隔离的 DidIdentity 角色校验 · 加密存储 · 锁/CAS · 恢复 · 生命周期
↔
外部协作模块 DID Publisher / Resolver HTTP Client · E2EE Session · Secret Provider

1. 强类型 E1 输入与角色矩阵

创建前校验 profile、域名、KID、服务和扩展。每类密钥固定算法、来源和 DID relationship， 例如 request_signing 必须是 Ed25519，并被授权在 authentication 中。

2. 加密托管且不可导出

托管密钥记录使用 ChaCha20-Poly1305 加密；每条记录的密钥通过 HKDF 派生，并把元数据纳入认证数据。 对外只暴露基于 KID 的操作。

3. 并发控制与事务恢复

所有变更和恢复都取得 store 级跨进程独占锁；generation/CAS 拒绝陈旧句柄覆盖新状态； journal 使中断的创建和更新在 reload/open 时恢复。

4. 两阶段 DID 更新

模块先准备候选文档，再由宿主发布。若发布结果不确定，必须读取并验证远端文档后 reconcile， 不允许盲目 commit 或 abort。

一次典型调用如何经过边界

应用指定
DID + KID + 操作
→
检查身份归属、角色、来源与状态
→
内部解封托管密钥并完成密码学操作
→
只返回签名或公开结果
03 · Modules

核心模块与重点功能

当前实现刻意保持单一职责：输入、文档、密钥、存储、生命周期和绑定边界可以独立审查。

模块 职责 关键保证
input.rs E1 创建/更新输入、角色矩阵、KID、服务与扩展校验 拒绝不支持的 profile、角色/算法组合和含私钥参数的 JWK
document.rs 构造 DID 文档、统一编码公开密钥、验证根证明 外部输入先解析为公钥材料，再由本模块生成规范化 VM JSON
platform.rs Injected、环境变量、本地文件与 OS keyring 根密钥提供者 provider 与 fingerprint 固定到 manifest；错误 provider 不会静默回退
keystore.rs 托管私钥的加密记录、HKDF 派生、AAD 和 secret reference 磁盘不保存明文私钥；每条记录独立派生；篡改可检测
store_lock.rs 跨进程文件锁与私有锁文件 所有状态变更与 recovery 在同一个独占写边界内完成
store.rs / registry.rs manifest、身份注册表、generation、元数据、journal provider pinning、CAS 冲突检测、多 DID 注册与崩溃收敛
identity.rs DidStore / DidIdentity 聚合接口、创建事务、打开与 reload 一个身份句柄只能访问自己的命名空间；冲突必须刷新后重试
lifecycle.rs 更新准备、发布协调、reconcile、退役、吊销与本地 crypto-erasure PublicationUncertain 只允许通过远端观察来消解
crypto_ops.rs Ed25519 sign/verify、X25519 ECDH、DID-WBA、HTTP Message Signatures 每次调用执行 KID 角色/来源/状态校验；拒绝无效和低阶 X25519 输入
secret.rs crate-private、zeroizing 的秘密值类型 秘密类型不进入公共 API，也不实现会泄漏内容的展示与序列化路径
bindings/node 异步 Node.js / TypeScript N-API 绑定与错误映射 阻塞 IO/锁/密码学进入 blocking pool；公共声明面不出现私钥类型
api/ + 快照测试 Rust API、N-API 与 TypeScript 声明的边界门禁 新增导出必须显式进入评审，降低无意泄露和兼容性漂移风险

E1 v1 的密钥角色

角色 算法 允许的托管操作 DID relationship
root_control Ed25519 仅模块内部的 DID 文档根证明 authentication, assertionMethod
request_signing Ed25519 通用签名、DID-WBA、HTTP 请求签名 authentication
e2ee_signing Ed25519 应用负载签名 assertionMethod
e2ee_agreement X25519 ECDH keyAgreement

每个身份必须有且只有一个托管的 root_control。外部公钥可用于验证， 但不会使 ANP Identity 获得对应的私钥能力。

04 · Collaboration

怎样与其他模块配合

ANP Identity 负责本地身份控制面；协议原语、网络传输、远端发布、消息会话和产品交互由相邻模块完成。

协作方 向 ANP Identity 提供 从 ANP Identity 获得 边界说明
anp crate 无状态 DID/签名/验证协议原语 状态托管、密钥隔离和生命周期层 ANP Identity 复用它，不复制协议实现
宿主应用 / DSH 存储路径、策略、用户意图、审批、网络调用 公开文档和受控密码学操作 宿主不应把任意字节签名开放给模型或不可信 UI
DID Publisher 把候选文档发布到 DID 对应位置 candidateDocument 与发布状态机 模块不发 HTTP，也不托管 did.json
DID Resolver 经验证的远端 DID 文档 reconcile 结果或冲突 不确定发布必须先 resolve，再 reconcile
HTTP Client 方法、URL、头、body，并负责实际发送 HTTP Message Signature headers 签名后不能改变被覆盖的请求组件
E2EE Session 对端 X25519 公钥、协议上下文、HKDF 参数 原始 X25519 共享秘密 会话密钥派生、ratchet、加密消息均由调用方负责
Secret Provider 随机 32 字节根密钥或平台凭据 根密钥加密保护的身份记录 可选 injected/env/local file/OS keyring；provider 固定在 manifest
AWiki IM Core 账号、消息、群组、附件与端到端业务编排 底层 DID 身份与密钥操作 完整 AWiki 插件应通过 IM Core 组合，而不是让本项目重做业务层
关于原始 ECDH 结果：它不是可直接使用的会话密钥。调用方必须把双方身份、协议版本和用途作为上下文， 使用域分离的 HKDF 派生会话密钥；Node.js 调用方还应在派生后主动覆盖返回的 Buffer。
05 · Scope

它解决什么，不解决什么

明确边界比列出更多能力更重要。下面是 v0.1 / E1 v1 的承诺，不代表未来路线图。

解决

  • ANP E1 DID 文档创建与公开元数据管理
  • 托管私钥的加密持久化与不可导出 API
  • 多 DID 隔离和按 KID 的角色授权
  • Ed25519 签名/验证、X25519 ECDH
  • DID-WBA 与对外 HTTP 请求签名
  • 请求签名密钥轮换和服务条目更新
  • 跨进程锁、generation/CAS、崩溃恢复
  • 退役、吊销与显式本地 crypto-erasure
  • Rust 与异步 Node.js/TypeScript 调用

不解决

  • DID 文档的网络托管、发布和 resolver 缓存
  • HTTP 传输、重试、证书与服务端验签部署
  • E2EE 会话、消息协议、ratchet 和消息存储
  • AWiki 注册、Handle、OTP、会话、群组或附件
  • 私钥导出、备份、root provider rekey
  • root_control 轮换
  • K1、PlainLegacy、P-256 legacy profile
  • 浏览器 WASM 或纯前端使用
  • HSM / Secure Enclave / 独立 KMS 或进程隔离
威胁模型边界：“私钥不可导出”是 Rust 公共 API 与 FFI 的逻辑边界，不是独立安全进程。 恶意 native addon、被攻陷的宿主进程、调试器、core dump 或本机内存读取者不在 v1 防护范围内。 同时拿到本地 root-key 文件和加密记录的攻击者可离线解密。
06 · Usage

其他程序怎么使用

集成遵循同一模式：选择 root provider → 打开或初始化 store → 创建/打开 identity → 按 KID 调用能力。

当前发布状态：0.1.0 仍是 pre-release；registry 发布等待协调发布 anp 0.9.4。 当前源码构建需要把 anp 与 anp-identity 作为同级目录检出。不要把尚未发布的安装命令写进生产部署脚本。

Rust：打开已有身份并按 KID 调用

use std::path::Path;

use anp_identity::{DidError, DidStore};

fn main() -> Result<(), DidError> {
    let store = DidStore::open_local_file(Path::new("./identity-store"))?;
    let identity = store.open_identity(
        "did:wba:agent.example.com:agents:alice",
    )?;

    let message = b"application payload";
    let signature = identity.sign("#request", message)?;
    identity.verify("#request", message, &signature)?;
    Ok(())
}

Node.js / TypeScript：创建身份并签名

const { DidStore } = require('@agent-network-protocol/anp-identity')

async function openOrCreateStore(root) {
  try {
    return await DidStore.openLocalFile(root)
  } catch (error) {
    if (error.code !== 'store_not_found') throw error
    return DidStore.initializeLocalFile(root)
  }
}

const store = await openOrCreateStore('./identity-store')
const identity = await store.createIdentity({
  profile: 'e1',
  domain: 'agent.example.com',
  pathSegments: ['agents', 'alice'],
  capabilities: { didWba: true },
  managedKeys: [
    { fragment: 'root', role: 'root_control' },
    { fragment: 'request', role: 'request_signing' },
    { fragment: 'agreement', role: 'e2ee_agreement' },
  ],
  externalKeys: [],
  services: [],
  extensions: [],
})

const signature = await identity.sign(
  '#request',
  Buffer.from('application payload'),
)

为对外 HTTP 请求生成签名头

const method = 'POST'
const url = 'https://api.example.com/messages'
const body = Buffer.from(JSON.stringify({ message: 'hello' }))
const originalHeaders = [
  { name: 'content-type', value: 'application/json' },
]

const authHeaders = await identity.httpSignatureHeaders(
  '#request',
  url,
  method,
  originalHeaders,
  body,
)

// 由你的 HTTP client 使用同一个 method、url、headers 和 body 发出请求。
// 任何被签名的组件在这里被修改，服务端验证都会失败。

Root provider 怎么选

  • Injected bytes：宿主已有 secret manager/KMS 取密能力时优先。
  • Environment：适合由部署系统注入 base64url 32 字节随机密钥。
  • Local private file：适合单机 CLI/服务；Unix 上创建为 0600。
  • OS keyring：适合有稳定系统凭据服务的桌面环境。

并发冲突怎么处理

  1. 收到 conflict 后调用 store 或 identity 的 reload()。
  2. 检查其他进程已提交的新状态。
  3. 重新判断原操作是否仍然有效。
  4. 仅在仍有效时重试。

Reload 会取得 store 级独占锁并执行 recovery，不应作为高频廉价轮询。

07 · DSH Plugin

作为 DSH 插件，还需要做什么

ANP Identity 已经是可供 Node 宿主调用的 native identity runtime，但它还不是一个完整 DSH 插件。 插件化的重点不是再写一遍密码学，而是定义安全的产品级服务边界、生命周期与可分发产物。

先决定插件范围

Recommended for identity-only

只提供本地身份能力

DSH/Cordis adapter 直接依赖 @agent-network-protocol/anp-identity，提供身份状态、 公开 DID 文档、受控 HTTP 认证和审批后的轮换。

Recommended for full AWiki

提供完整 AWiki 能力

DSH 插件依赖 @awiki/im-core-node；由 awiki-im-core 在内部组合 ANP Identity。 注册、Handle、消息、群组和附件不应在本项目重复实现。

Not supported

纯浏览器身份插件

当前实现是 Rust N-API native addon，没有 WASM/浏览器运行时。浏览器 UI 只能通过 DSH Remote 调用 host 侧服务，不能直接导入 native package。

建议：如果目标是“DSH 中可复用的 ANP 身份服务”，做薄的 identity-only 插件； 如果目标是“DSH 中使用完整 AWiki”，继续走 dsh-awiki → @awiki/im-core-node → awiki-im-core → anp-identity， 不要让 UI 或工具绕过 IM Core 直接操纵底层身份状态。

推荐架构

DSH UI / Model Tools 只访问安全 DTO 和窄能力工具
→
Cordis Service + Provider 审批 · 生命周期 · 多租户映射 · 错误策略 host-only adapter 调用 ANP Identity Node binding
↔
Host resources stateRoot · Secret provider DID publisher / resolver · native package

需要补齐的工程项

1

冻结插件契约

定义 Cordis service、provider、consumer、配置 schema、Remote DTO、错误码和 model tools。 明确 identity-only 还是 full AWiki；动态配置错误应 fail-loud，不能静默回退到另一身份或另一 provider。

2

把 native binding 做成可安装产物

为 DSH 支持的 Node ^22.19.0 || ≥24 验证 ABI，并按 Linux/macOS/Windows、x64/arm64、 必要的 libc 组合产出预编译包。运行时安装不能要求 Rust、同级 anp checkout 或联网下载构建依赖。

3

实现 host-only 生命周期

每个 deployment/tenant 建立明确的 stateRoot 与 DidStore 所有权； 用 ctx.effect 注册和清理 provider。插件关闭时拒绝新调用、等待 in-flight 操作完成、 释放引用，且 close/dispose 必须幂等。

4

接入发布与解析

配置 DID 域名和发布凭据，提供 publisher/resolver adapter；把发布超时写入 PublicationUncertain，由后台任务或用户操作 resolve + reconcile，绝不盲目 abort。

5

设计安全工具面和审批

默认只开放读取状态、读取公开文档和预定义 HTTP 认证流程。创建身份、轮换、发布、吊销、 crypto-erasure 等改变状态或不可逆操作必须经过 user presence/approval。

6

补齐验证、供应链与运维

增加插件契约/快照测试、真实 Harness 装载与热重载、跨进程 state lock、打包后 clean install、 native 平台矩阵和远端发布 E2E；同时产出 LICENSE/NOTICE、SBOM、checksum 与 provenance。

模型工具面：应该开放什么

适合开放

  • 查询 identity 列表与健康状态
  • 读取 DID、公开文档和公开 KID metadata
  • 通过固定 endpoint/purpose 的 HTTP 认证适配器发起请求
  • 查看 pending revision 和 publication 状态
  • 生成更新预览，在审批后执行发布

不应直接开放

  • sign(kid, arbitraryBytes) 任意签名 oracle
  • 任意 URL、任意 header 的无约束 HTTP 签名
  • root-control 的直接调用或根密钥读取
  • 未审批的吊销、删除和 crypto-erasure
  • 把 stateRoot、root key、env 名称或本机路径返回 UI

真实环境验收

Harness 装载/卸载、崩溃恢复、跨进程竞争、远端发布、平台矩阵和安全回归全部通过后再扩大使用。

完成定义：DSH 能在无 Rust 工具链的干净环境安装插件；秘密只存在 host 侧； UI 和模型拿不到通用签名 oracle；插件可安全 reload/dispose；发布不确定性可恢复； 身份、租户和存储路径不会串线。
